Vancouver Regulation Toolkit

ARCH 540 Designing the Design · UBC SALA · Fall 2026 · Assignment 1, reviewed October 2, 2026

Assignment 1 asked each student to take one piece of a Vancouver regulation or design guideline, understand it, and build a small interactive tool with Claude that explains, computes and visualizes it, so that someone else can use the rule without the author in the room. Four weeks, one tool per student. Each entry below has the student’s own one-sentence brief, a link to the tool, the live demo from the review, and the discussion that followed.

Curbside

Jenna Bruggeman
Open the toolRepositoryWalkthrough video
Curbside helps anyone from a café owner to a designer turn an idea for a Vancouver parklet into a site-specific proposal that's checked against the City's Parklet Manual as they design.

Place a parklet on a real Vancouver curb from OpenStreetMap, generate layouts from program priorities, arrange furniture and check clearances, street widths and sun against the Parklet Manual. Exports a schematic or technical review package and a Rhino model; every check cites its source and says whether it is a provisional or confirmed pass.

Discussion at the review
  • How do the priorities drive generation? They bias the scheme: umbrellas appear if shading ranks first, and a low seating rank yields more open space instead of furniture. Material preferences are still being built out, and the parklet footprint can also be drawn freehand, for instance as a linear parklet.
  • Add a chatbot inside the tool that captures the user's goals in plain language and translates them into the existing preset parameters, rather than giving it free rein; that stays controllable and user-friendly. The report and the side-by-side comparison of design options and trade-offs were singled out as strengths.
  • The tool suits a restaurant owner working alone as well as a full design package submitted to the city; the drag-and-drop experience feels gamified in a good way.
  • On how the interface became so polished: UX research, design skills such as "impeccable", stripping out generic AI patterns, feeding design standards and visual references, and many rounds of iteration. The skills will be shared with the class. Two routes were suggested for others: UI skills (impeccable, frontend-design) and a Claude Design round trip, i.e. develop a visual language in Claude Design and import it, or upload the project, restyle it there and export back.
  • An exciting starting point, but the start-to-finish experience is complex; would a coffee-shop owner or a designer know what to do? The object library is a highlight. A next step is embedding design intent or a concept, not only placing objects. The current object style is a little gimmicky, which may matter if an AI later re-imagines the render.
  • Importing your own furniture is built but untested. The bigger ambition: export the whole parklet to Rhino, model it there and plug it back in, so the design becomes truly the designer's own.
  • Rendering control deserves exploration: each furniture asset already has a 3D model, so pairing it with material and product photos would allow a curated rendering workflow (an AI moodboard collage that places the furniture images into the render at the right spots). In industry the open issue is renders whose furniture is actually purchasable; a report of where to buy each item would follow naturally.
  • Furniture placement can snap to a toggleable grid, and measurements can be checked.
  • Keyboard shortcuts were requested: Ctrl-C/V to copy, R to rotate, Shift to multi-select a table set and move it together. Not set up yet.
  • Tree sizes cannot be changed because the trees are the real street trees from Vancouver's open data; planting new trees could be added.

    Stair Core Tool

    Guoxian Xu
    Open the toolRepository
    Sizes and lays out the exit stairs of a building core to the Vancouver / BC / national building codes, then checks exit separation and travel distance on your floor plan.

    Computes exit stair count, clear width, flights and enclosure size from floor areas, occupancy and storey heights, following VBBL 2025, then BCBC 2024, then NBC 2020, with each value tagged to its clause. A second part traces walls on an uploaded plan and runs a travel-distance heat map.

    Discussion at the review
    • Can it read JPG/PNG plans? Yes, but pixel-based detection works poorly; the vision step was done in GPT and the result handed to Claude Code, since GPT's vision is stronger.
    • The first thing to improve is the interface: decide the minimum information a first-time user needs, surface the main function (currently in the bottom-left corner) and hide secondary information behind toggles.
    • Reading raster plans into walls is a genuinely hard problem that firms employ full-time people on. For a prototype it is enough to prove the workflow and state clearly that this step can be solved by current or near-future vision models; the manual tracing fallback already exists.
    • For the travel-distance check the walls do not need to be accurate; a rough sketch is enough, and the example was traced in about a minute.
    • The first part sizes stairs at the code minimum; the plan part lets you enlarge them, and a stair turns red if shrunk below the minimum.
    • What about floors with different storey heights? The calculation is based on the ground floor, i.e. the largest demand.
    • The two parts feel disconnected. Consider making the plan the main interface, with stair details in section, and link them: changing a door side in the plan does not update the 3D or section view, and tall ground floors or different door positions per level should flow through. A split view where plan edits update the 3D would close the loop.
    • Since detection reads poorly, would a plugin for a modelling tool (Revit) be better than a web page? The web version is deliberate: testing needs no accuracy and takes a minute, where a modelling workflow takes longer. It is a scope trade-off between easy-to-use and accurate; as an early-stage tool it is very easy to use. Worth thinking about how first-year students would be encouraged to use it.

      R3 Zoning Feasibility Study Tool

      Yeoneui Kim
      Open the toolRepository
      R3 zoning allows small apartment buildings on what were single family housing streets, and this tool shows what a given lot can hold under the zoning and building code, including Vancouver's new single egress stair rules.

      Pick an R3 lot, see the permitted density and what assembling parcels adds, choose storeys and layout preferences, generate a unit plan and read a code summary of what is met. Also a test bed for the single-egress stair rule.

      Discussion at the review
      • Making the user walk through each code item, so the design "plops out" of the code, is a strong step that makes the logic very clear.
      • The hardest part was unit generation. The model reads rules well but lacks architectural judgement, so early units were hideous. The problem was bounded (a guided prompt with limits) while leaving the user some freedom. Workflow: export the plan as JSON, feed it back with critique so Claude learns the preference; after the class on loops, agents that learned those preferences ran ten layouts through five feedback rounds. Results improved but still produce odd plans.
      • Let people test the tool for a period and review the generated designs so it learns which floor plans not to produce.
      • The embedded generative feature is a strength, as is feeding domain knowledge or an expert's own criteria through a multi-agent workflow. Opportunity: a firm could upload its own unit, window and door libraries and ask the AI to adapt that library to the plan and iterate.
      • The graphics look much better on the Zoom screen than on the projector.
      • User-experience feedback was requested specifically, since interface design was left out of most people's process. Reviews are not limited to the two assigned reviewers; they can go to GitHub issues or the class deck's speaker notes.

        Vancouver Solar Shading Explorer

        Willem Girard
        Repository
        A tool for designers to understand solar geometry and solar heat gains, and iteratively design code compliant exterior shading devices.

        Move the sun in 3D, by slider or on the sun-path chart, and watch shadows and solar heat gain change per window, floor or facade. A recommendation panel proposes the ideal horizontal or vertical device for that instant and checks it against the by-law overhang limit.

        Discussion at the review
        • "I wish I had this" for an earlier studio.
        • Can you change the input building or upload your own model? Not yet; it exports to Rhino. Floors are arrayed recursively (each matches the one below), and rotating floors produced a twisting tower live; a "match floors above" checkbox applies changes upward or keeps a floor unique.
        • Geolocation: Vancouver weather files for now, but any weather file could be used, and the regulation values can be edited for another jurisdiction.
        • Make the facade parametric so that when the building rotates the devices update with the sun angle, and let the tool optimize the shading automatically.
        • Extend the facade typologies: the common market types and more designed types, and work out how to parameterize each so devices fit it. Operable external shading (the European rotating type) was raised; the devices already twist.
        • Self-critique: too many settings; window types, window systems and four sides per floor make it hard to find what you want to edit. Decide the minimal information to present. A commercial product that builds parametric facade skills into its interface, with an icon per facade type applied to the building, was cited as a reference for a straightforward interface.
        • The 3D angle globes are nice to look at but overwhelming when making graphics; they can be turned off, and a more minimal default was planned.
        • Viewports can be customized and saved, like Rhino; the limit is screen size.

          MassShadeLight

          Ayden He
          Open the toolRepositoryFull demo requires downloading the package (Rhino link).
          It shows architects how massing, windows and shading choices affect daylight and overheating against the Passive House limit (no more than 10 % of annual hours above 25 °C), as quick estimates for comparing early design options, not energy simulation.

          Adjust massing, notches, atrium and shading devices and see daylight and overheating diagrams update live, with the model rebuilt in Rhino through MCP. Devices are learned from images and stored in a repository; iterations can be saved and compared.

          Discussion at the review
          • A big development since the last check-in. This is effectively a Rhino plugin with a web interface, which is one of several possible formats: a true Rhino plugin, where panel, parameters and analysis layers all live inside Rhino; a web interface with Rhino running in the background (for instance streaming screenshots into the page) so everything is in one window; or, for a wider audience without Rhino, Rhino Compute, a rented cloud Rhino that gives Rhino and Grasshopper capacity to a web page much like three.js.
          • An earlier web-only version ran much smoother; the plan is to bring the interface back to the web, let Rhino or Rhino Compute compute in the background, and pull Ladybug/Radiance data back into the page.
          • The target user decides the format: the public has no design software, designers do and a plugin suits them. Presets of shading patterns would help as a starting point, and shading could be tied to interior program, since room use changes shading needs; massing could then be optimized with program.
          • Another small tool already weights program needs (light, heat, views) per plan cell and auto-populates program into the plan; the current tool combines pieces of several small tools.
          • The design question matters: the Solar Shading Explorer covers standard facades, this tool very non-standard ones; what lies in between, and what library makes sense (the most common Vancouver facades, how non-standard to go)?
          • Devices that change through the day (a kinetic facade): a building-rotation parameter exists and devices could be linked to sun angle over time; not done yet.
          • Self-critique: the topology-operation interface is not intuitive (defining a notch and how many floors it penetrates), and the performance data could be summarized into recommendations designers can read. Much existing research on interpreting thermal environments and curating facade types is worth drawing on if this becomes a serious project.

            Lotwise

            Kaili Sun
            Open the toolRepository
            Lotwise reads and checks any R1-1 lot against the zoning schedule, draws the permitted envelope, creates massing options, floor plans, site plan and section so a schematic multiplex design can be tested on a real site in minutes.

            Checks any R1-1 lot clause by clause, draws the permitted envelope, then builds massing options or test-fits the CMHC housing catalogue, producing floor plans, site plan, section, 3D view and a step-by-step report. Floor plans are still rough.

            Discussion at the review
            • Do the CMHC options produce the CMHC plans? Not exactly; the catalogue's schematic plans were fed in so the generated layouts resemble their circulation, plus clearance rules (915 mm exterior doors, 815 mm interior) and area minimums (105 m² three-bed, 80 m² two-bed). Areas are right; furniture layouts are not.
            • CMHC is releasing construction documents, which could be good training material.
            • Floor-plan generation is a large research area in computational design: image-based methods trained on colour-coded room datasets, and graph-based methods where rooms are nodes. There are ways to make generation more controllable; for this stage the tool is already useful and user-friendly.
            • Drop the furniture. For an early-phase developer tool, room labels and sizes are enough; even rooms may be distracting. Show units as blocks with areas and bedroom counts (an 800 sf one-bed, a 2,000 sf two-bed); unit and fire separations matter more than room layouts. It depends on who uses the tool and at what stage; a later-stage tool would focus on plans. Rules can also be set room by room; if sizes and connections are right, furniture is unnecessary.
            • Topography is read from Vancouver data via OpenStreetMap rather than official GIS, because GIS produced blotchy patches in the map. Verify against real sites so that a maximum building height is not skewed by a bad ground level; even GIS data would need a site survey as ground truth. The 2009 Vancouver building-footprint and lot dataset has lot geometry and elevation.
            • The exit stair is not yet editable but should be; stair placement matters a lot in R1-1, and a shared single exit was explored but needs more rules.
            • The street front is pulled from data (the wider street). Corner lots are not yet handled (different frontage requirements); lots without a rear lane are another fringe case that rules out sixplexes and accessory units.

              Pocket Studio

              Balreet Dhatt
              Open the toolRepository
              A laneway house tool that allows you to find your lot, shape a laneway house to Vancouver's R1-1 by-laws, plan every room, render 3D models and download drawing sets, all in a single browser-based tool.

              Seven steps from lot to laneway house: presets, parametric position and the 4.9 m separation rule, walls, roof, windows and doors with schedules, floor plans, sun path, compliance check, materials and renders, and a report. Exports NURBS models and drawings to Rhino.

              Discussion at the review
              • Joking verdict: it looks ready to issue for construction.
              • Floor plans are the weak part; CMHC drawings were referenced but did not translate.
              • Materials and textures: the tool was first asked to code them, then specific materials were requested (a Belgian brick). More would have been done with more tokens, since the floor-plan work used up the credits.
              • The UI style and transitions are intuitive. The first version had generic AI styling (pill-shaped forms); a web-design interface skill with standards was uploaded, then the interface was iterated many times. "Impeccable" was not used because it is a Claude Code skill and the project was built in Claude chat; linking the project folder in Claude Code and running the skill to review the UX was suggested.
              • Working tips: change one panel at a time so versions can be compared; when changing a design decision, ask for prototypes first and choose from visual options.
              • Ceiling heights and roof pitch stay within code: the check reports "half a metre too high" and the user adjusts. An auto-conforming version was tried but it takes control away from the user.

                Downtown Massing Tool

                Sinnie Choi
                Open the toolRepository
                This tool allows designers to test different tower massing options in Downtown Vancouver and understand how their designs measure up against building code requirements and local planning limits.

                Select a downtown site and get site facts plus FSR, height and setback limits derived from the planning documents (flagged confirmed, derived or needs verification), then shape one of four tower typologies and read a compliance list that points into the model. Versions can be saved and compared; a live report exports as HTML.

                Discussion at the review
                • The icons for design strategies and typologies and the version comparison were singled out.
                • It would be cool to push the massing into Revit as a design assist.
                • A floor-plan feature was started, but service spaces come out invisible; an exit-stair travel-distance check shows dead ends (it works on parking levels, not yet on residential floors). Trying to put too much into one tool.
                • How was the layout generation prompted? Minimal prompting worked best: start by asking it to calculate exit distance from walls and doors to stairs, which worked; when plans went strange, switch to a distance colour map; and ask it to study cases online before generating.
                • The home-count estimate is based on the unreliable plan generation, so don't rely on it; the parking-stall count is more reliable.
                • Masses can be dragged in plan, with precise adjustments; floor-plate adjustments are buggy.
                • A red dot hints at problem floors; individual floors can be locked; the parking ramp function exists but does not really work yet.

                  Root Room

                  Kaiyan Huang
                  Open the toolRepository
                  Vancouver's street tree standards say how much soil each size of tree needs, but not where that soil can fit on a real street. Root Room starts from a real Vancouver street and tests how redesigning the ground (soil depth, soil system, connected soil space) changes the size of tree it can carry.

                  Applies Vancouver's soil-volume standard for street trees to a real block: change soil depth, soil system and street width and see which tree sizes the ground can carry, in plan, section and axonometric. Compare scenarios and export a report for the planting plan.

                  Discussion at the review
                  • This fits researchers as much as designers; the depth of research into soil and tree types and the academic graphic style stand out; a good landscape counterpart to the architecture tools.
                  • Section drawings per tree are vector drawings assembled from different sources; a full library was wanted but there was not enough room, so colours distinguish species.
                  • Add "?" explanations under the soil systems (structural soil, soil cells, credited vs. visible soil). Native soil counts fully; engineered soil counts about half for planting.
                  • Is there open data on soil contamination? The city was emailed for soil data; Toronto has a soil calculator; for now Rhino is used to calculate depths and volumes.
                  • A tool can also be built for yourself, to organize information and learn a topic. The isometric view is strong; finish it (it is token-heavy) and use it as the promotional image on the homepage.
                  • Predict root depth and spread in the section and project tree growth over time, so architects can see where excavation and new buildings interact with trees; a bridge between landscape and architecture. A former student's GP project had a website of root plans in 2D; that data has been requested so different tree ages can be shown.
                  • The building–tree relationship matters: roots grow differently next to existing buildings and depending on nutrition; add the time dimension and seasonality; canopy size and seasonality can all be parameters in the 3D tree.
                  • General housekeeping: if GitHub limits are hit, apply for an education account; as tools get heavier, organize complexity (split one HTML file into a structure of pages, load 3D context only for the region in view); periodically ask Claude, in a fresh session, to clean out unused files before pushing.

                    R1-1 Permeability Tool

                    Kevin Jinn
                    Open the toolRepository
                    This tool helps designers comply with the impermeability bylaw for the maximum amount of building and hardscape that can be built on R1-1 lots, as well as how different percentages of permeability affect stormwater management in the city.

                    Checks the 75% impermeable and 50% building limits on one R1-1 lot with editable paving figures, and a city-wide slider that colours every lot and translates the share into stormwater volume against the Rain City 40% target.

                    Discussion at the review
                    • Architecture by-laws are hard to separate because they condition each other; this landscape rule is refreshingly cut and dry.
                    • Why is the red always on the south side of each lot? It is a visual ratio, not spatial, and it reads as spatial when zoomed in. A gradient (blue to red) would be clearer and works better when zoomed out while sliding the percentage. More generally, different visualizations per scale: 3D height for permeability, or a gradient whose range can be set to 0–100% or 20–80%.
                    • Is 40% the rule of thumb for a new site? Yes, the Rain City target, though not always achievable.
                    • Some lots are not coloured (a block on the right); whether they are R1-1 and why the data is missing will be checked.
                    • Data: GIS plus the 2015 building footprints; the 2022 LiDAR (gigabytes) was not used.
                    • Focusing on one niche of the by-law is valuable at the planning stage, and very helpful for a planner looking at the big picture.
                    • A regulation applies to one lot but collectively shapes a larger form and informs decisions; link the map to quantitative layers (topography and even a basic runoff analysis, parks, hidden streams and creeks, rainwater infrastructure) for storytelling and for redesign at this scale. Landscape rules are not easy to isolate either; topography is the acknowledged limitation.
                    • A planning argument: lots on the original natural streams should provide more permeable area, lots on ridges could take more impermeable surface, diverting water back to natural streams; this could become a parametric rule.
                    • What counts as permeable? Concrete and asphalt are impermeable; soil to a certain depth, and gravel of a certain size and depth, count as permeable. The purpose is stormwater and flood management, and the rule stops clients from paving everything.

                      Bikeway Designer

                      Felicity Li
                      Open the toolRepository
                      Enables planners and community members to create bikeway proposals that build upon Vancouver's existing network, following TransLink's Rapid Implementation Design Guide for Bikeways, CoV's All Ages and Abilities Design Guidelines, and CoV's Engineering Manual.

                      Build a bikeway proposal block by block on the existing network, verify inferred lane and parking conditions against street view, choose protection type and lane widths against the Engineering Design Manual, and watch a bike score update live, in plan, section and 3D.

                      Discussion at the review
                      • After so many abstract massing tools, it is grounding to see the actual city and street view; the panning design view is neat.
                      • Combine the Nano Banana rendering idea with the Google Street View panel: screenshot the street view and render the proposed lane onto it.
                      • Overlay the impact of the change on traffic conditions, if such data exist; planners would love it, but adding a lane often removes parking, so the consequences should be visible. This feature is already planned.
                      • A navigation mode: route from A to B using only bike lanes and score a route by how many metres lack protection; from there, recommend where lanes are most needed rather than leaving the user to guess. Geographic research on where lanes are needed could drive the recommendations.
                      • How is the bike score calculated? AI-calculated from a UBC study of bike scores in Vancouver (incline, protection, redundancy with parallel routes), not yet validated. That is fine if grounded in the research; cities compute bike scores differently (slope, points of interest, traffic).
                      • Safety at busy intersections (right-turning cars, bike signals); include traffic lights. Vancouver open data has bike-crash counts per street, a useful reference for where protection is needed.
                      • Small UI tweaks: rename toggles to something more intuitive (compare, design); allow design elements along the lane, as the building-design tools do.
                      • A really exciting tool; intersections make it infinitely more complicated.

                        Massing Studio

                        Claudio Cabana
                        RepositoryRuns locally with Rhino MCP; see the README.
                        Create a Rhino3D massing that exports to a code summary for collaboration with code consultants.

                        Set up a lot, storeys, setbacks and glazing, then export the massing to Rhino and keep editing there; every save flows back through Rhino MCP. The code check returns occupant load, exits, travel distance, washroom counts and limiting-distance flags, exported to Excel for the code consultant.

                        Discussion at the review
                        • A good point in principle: do not rebuild city 3D modelling in the tool; Rhino already does that, so use Claude to build only the missing part. That is the real workflow.
                        • Setting up a site in Rhino (GIS, cropping, big files) is the hated part; the aim is to get straight to the puzzle (how many washrooms and exits) and start designing; a code consultant will do the real compliance later.
                        • Is this the MCP? Yes, which is why it must run locally; the GitHub README lists both the web page and the local app.
                        • Glazing and limiting distance are stored per block, 50% on all faces by default and editable. The six flags are mostly occupancy adjacencies and fire separations to work out with a consultant; "zoning not checked" is a bug to fix.
                        • Validation: an R3 project's construction drawings (elevations, sections, plans) were fed in and the generated code report compared with the consultant's code summary; it matched entirely. Classmates' studio projects could be checked the same way.
                        • What happens if new geometry is drawn in Rhino and saved? In a live test a new box was partly recognized (layers bumped) and an L-shape was not; the sync is more of an export-then-watch than a true two-way edit. A built-in layer system per occupancy would help; it can be fixed.
                        • A Rhino plugin was considered, but the saved-iterations view is nicer on the web; the site is not flat and 3D topography (as in Lotwise) is missing.
                        • The collapsible menus keep the interface simple and easy to explore.

                          Broadway Corridor Massing Tool

                          Joseph Tong
                          Open the toolRepository
                          A single-file, browser-based tool for testing building massing on any Vancouver lot against the Broadway Plan and the City's zoning schedules, with up to 1 km of surrounding buildings, streets, parks and zoning drawn as a 3D diagram.

                          Type an address along Broadway to load the lot, 1 km of context and the Broadway Plan pre-zoned envelopes, assemble parcels, and size a podium-and-tower massing to the FSR cap or propose a rezoning.

                          Discussion at the review
                          • Is density tied to FSR nodes? Upzoning is highest right around stations and lower farther away; the tool tests maximum density only.
                          • LiDAR, OpenStreetMap, another dataset and topography were tried, but old topography did not align with building heights and footprints, so the model was simplified.
                          • The modelled site is not visually distinct from the highlighted envelopes; make it clearer. There is no warning when the limit is exceeded; the user clicks the FSR-cap button, and a warning could be added.
                          • Besides the FSR cap there are no other indicators yet; you tweak the building and try a proposal.
                          • A shadow study would be easy to add with a few preset views and times.
                          • Density is also regulated by the Broadway Plan and transit-oriented areas (minimum heights around stations).
                          • The coloured boxes show height limits for other sites but not for the site being massed; represent what you are allowed to build on your own site in the corridor.
                          • A bigger question for everyone: visualize the maximum or minimum mass across a whole district, so the regulation landscape informs collective form rather than single buildings. Change one parameter at district level and quantify the result (population, traffic) before and after rezoning; planning departments run such rezoning studies (in some cities a "reasonable worst-case scenario" study) on hundreds of sites, and this logic could support that.
                          • The greyed-out parcels are industrial mixed-use and cannot be rezoned.

Flagged as very important.

                              SRO Conversions in the DTES

                              Bridgette Kelly
                              Open the toolRepository
                              This tool visualizes tenant displacement on the urban scale caused by SRO conversions in the DTES. It allows users to explore scenarios through altering different thresholds set by the DTES Plan and SRA Conversion Guidelines.

                              Maps 142 DTES SRO buildings and simulates how the unit-size minimum, retention cap and conversion targets displace tenants, per building and per person, with a compensation estimate. Three preset scenarios plus adjustable thresholds.

                              Discussion at the review
                              • Are these the actual plans of each building? Derived, not surveyed: building area from footprints, units per building from a survey inventory, floors from LiDAR, giving units per floor and area per unit; Claude did not understand real architectural layouts, so the plan is generated from those figures and the assumption sliders change it.
                              • The generated plans ignore building geometry (every building becomes a linear corridor). The set of buildings is finite, so the data could be curated better: use real floor plans where they exist (perhaps 30% of buildings) to sharpen the assumptions. Real floor plates were tried, but not every building is entirely SRO and corridors came out 10 m wide, so it was simplified. Claude could probably be trained to read these plans.
                              • The direction is good: not one building's form but a collective result, policy linked directly to data, with design knowledge embedded.
                              • The simulator of unit sizes and configurations and the effect on people is a highlight. A (defunded) public-housing project converting an East Vancouver warehouse into SROs at the city's unit minimums, with washrooms as a share of units, suggests applying the same logic to a potential adaptive-reuse site.
                              • The graphics are very good. Claude first produced one huge HTML file that became hard to edit, so it was split into smaller files per aspect; references were the student's own graphics, with descriptive language and six or seven options to choose from (about four reference images in total). The trees were their own sub-project (controllable line work, repeated attributes for performance) and remain the weakest part.

                              Comments
                                Cross-cutting remarks
                                • Interface quality is now a design task, not a by-product. Skills such as "impeccable" and "frontend-design" and a Claude Design round trip (import a visual language, or restyle and export) are the quickest ways to remove generic AI styling. Students who did this will share their workflow.
                                • Decide the minimum information a first-time user needs on screen; move everything else behind toggles. This came up for the stair tool, the shading tool and the massing tools alike.
                                • Floor-plan generation is the common weak spot. For early-phase tools, areas, unit blocks and adjacencies are enough; furniture and room layouts can be dropped. Where plans matter, controllable methods exist (rule sets per room, graph-based generation, preference loops with agents).
                                • Choose the format deliberately: web page, Rhino plugin, web page with Rhino in the background, or Rhino Compute for users without Rhino. Each student should state who the user is and pick accordingly.
                                • Several tools point toward the same next question: regulation as a collective, district-scale form rather than a single-lot check (massing envelopes, permeability, view cones, SRO policy).
